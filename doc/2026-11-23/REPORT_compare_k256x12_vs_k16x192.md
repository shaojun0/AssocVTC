# 周末两跑对比：256 token × 12 维（256²） vs 16 token × 192 维（448²）

- 写定：2026-11-23（周一）
- 对比对象（均为上周末跑）：
  - **A = 16 token × 192 dim @448²**：`tok448_zs192_t8_norfid`，2026-11-20 22:12 → 11-21 00:53
  - **B = 256 token × 12 dim @256²**：`tok256x12_t8`，2026-11-21 11:13 → 11-22 04:57（训练），随后同 ckpt 的感知/GAN 消融到 11-22 16:07
- 数据来源：本地 `tok448_work/artifacts/` 与远端 `/root/autodl-tmp` 逐文件 **sha256 核对一致**；两份 `fast_rfid` JSON 的 config/protocol 均已和远端 `s2/args.json`、`ckpt["cfg"]` 对账。

---

## 0. 一句话结论

**按"同一 3072 值/图"的绝对满速率质量，B（256×12）更好**：PSNR 22.67 vs 21.87 dB（+0.79）、rFID **86.50 vs 102.49**（−15.6%）。
但**这两跑不是受控 A/B**——分辨率（256² vs 448²，每像素码率差 3.06×）、初始化（从零 14ep vs 45ep 全宽 s1 + 3ep SVD 热启动）、预算（17.7h vs 15.6h 总时长）全都不同，所以**不能据此判定"多而细的 token 分配优于少而粗"**。

- 若按**每像素码率**对齐，反而是 A 更好（21.87 dB / rFID 102.5 vs B 内插 ≈20.94 dB / 134）⇒ 周末数据主要证明的是"**分辨率/口径对齐后绝对值变好**"，不是 token×dim 分配问题。
- 若**放开 8 步循环解码约束**，同 3072 值下项目最好的参照是 **T=1 的 16×192@448：25.25 dB / rFID 48.13**（同 init、同 3ep，只差 T=1 vs T=8）⇒ 当前主要短板是 **8 步循环读出本身（−3.38 dB、rFID 2.13×）**，而不是 token 数或维度。
- 要干净回答"哪个分配更好"，缺的是**同分辨率受控臂：256² / patch16 / K=16 / zs_dim=192**（从零、同 B 配方 14ep，约 17.7h）。

## 1. 两跑的事实（已与远端核对）

| 项 | A：16×192 | B：256×12 |
|---|---|---|
| 输入 / patch / N | 448² / 32 / **196** | 256² / 16 / **256** |
| 特殊 token 数 K | **16**（4×4 潜网格） | **256**（16×16 潜网格 = 全部 patch） |
| 每 token 瓶颈维 zs_dim | **192** | **12** |
| 满速率值数 | **16 × 192 = 3072** | **256 × 12 = 3072** |
| 8 步 cumulative 窗口 | 1,2,3,5,7,10,13,16 token | 32,64,96,128,160,192,224,256 token |
| 解码 | T=8 循环解码 | T=8 循环解码 |
| 初始化 | `tok448_v2/s1`（**45ep 全宽 16×1248**，13.05h）+ **秩-192 SVD 热启动**（相对误差 0.781） | **从零** |
| 训练 | 3 ep / 2850 步 / **153.6 min** | 14 ep / 13300 步 / **1063.9 min = 17.73h** |
| 总训练时长 | 13.05h（s1）+ 2.56h（s2）= **15.6h** | **17.73h** |
| 损失 | 纯逐像素 L1（rfid_weight=0） | 纯逐像素 L1（rfid_weight=0） |
| 参数 | 485.70M | 480.64M |
| 训练侧 best val（1024 图） | 21.83 dB（patchDC 18.07，+3.76） | 22.61 dB（patchDC 18.63，+3.98） |
| 满速率 8 步评测（5000 图） | **PSNR 21.87 / rFID 102.49** | **PSNR 22.67 / rFID 86.50** |
| 与 ALIT-S 8.25 的差 | 12.4×（但 448²，不可直接比） | **10.5×（256²、3072 值，与 ALIT 同口径）** |

> 引用修正（本次审计发现）：B 报告里"14 ep ≈ 13.7h"与日志不符，实际 **1063.9 min = 17.73h**；A 报告里"151.6 min"实际 **153.6 min**。后文预算比较一律用实际值。

## 2. 同一"3072 值/图"口径的逐点对比

| 值/图 | A 16×192@448² PSNR / rFID | B 256×12@256² PSNR / rFID |
|---|---|---|
| 384 | 20.61 / 146.7 | 19.04 / 178.1 |
| 768 | —（A 无此点） | 20.43 / 146.4 |
| 1152 | — | 21.26 / 126.3 |
| 1536 | — | 21.80 / 112.3 |
| **1920** | **21.73 / 106.9** | **22.15 / 101.6** |
| 2304 | — | 22.42 / 93.6 |
| 2688 | — | 22.58 / 89.3 |
| **3072** | **21.87 / 102.49** | **22.67 / 86.50** |

- 两条曲线在 384 处 A 更好（20.61 vs 19.04 dB；rFID 146.7 vs 178.1），在 1920、3072 处 B 更好。B 的曲线从 384 起步、A 从 192 起步，两者没有共同覆盖的低速率段。
- 满速率处 B **+0.79 dB / rFID −15.6%**；但从 1920→3072 的增量看，B 是 +0.51 dB / −15.1 rFID，A 是 +0.14 dB / −4.4 rFID——**B 在高速率端仍在有效利用新增 token，A 已经饱和**（A step6→7→8 的 rFID 几乎不动：106.87→106.43→102.49）。
- B 的快照证据：ep8 rFID 118.9 → ep12 90.9 → ep14 86.5（≈ −2.2/epoch），**14 ep 远未收敛**；A 只有 3 ep。两者的"训练程度"也不同。

## 3. 为什么这不是受控对比（三个混杂因素）

1. **分辨率 / 每像素码率差 3.06×。** 同为 3072 值/图，A 是 448²（**65.3 px/value**），B 是 256²（**21.3 px/value**）。B 实际上是在 3.06× 更高的相对码率下答题，rFID/PSNR 更好是预期内的。
2. **初始化与预算不同。** A 的 encoder/decoder 先在 448² 上做了 **45 ep 全宽（16×1248，13.05h）** 预训练，再 SVD 压到 192 维微调 3 ep；B 是 **12 维瓶颈从零** 训 14 ep（17.73h）。两条路的优化难度、总算力都不可比（A 总 15.6h、B 17.73h；方向相反地，A 有更好初始化、B 有更多从零预算）。
3. **"token × dim" 的语义本身也跟着分辨率变了。** A 是 **4×4 潜网格、每格 192 维**（每个潜向量覆盖约 12 个 32×32 patch）；B 是 **16×16 潜网格、每格 12 维**（一 patch 一码）。所以这不只是"16 个粗码 vs 256 个细码"，还叠加了潜网格分辨率（4×4 vs 16×16）与像素覆盖（112×112 vs 16×16 px/潜向量）。
4. **跨分辨率的 FID 绝对值严格来说不可比。** 审计确认 `fast_rfid.py` 同一份代码、同 5000 张 IN-100 val、同 InceptionV3 pool3/2048d/resize299/uint8 量化；但 GT 先按其 img_size 预处理（448 vs 256）再进 Inception，**GT 参照分布不同**。所以 86.50 vs 102.49 只能作"同设置内可信、跨设置指示性"的对比。

---

## 4. 换口径：按每像素码率对齐后，结论反过来

把 B 的曲线内插到与 A 相同的 values/pixel（B 等价值数 = A 值数 × 256²/448² = ×0.3265）：

| A 值/图 | A PSNR / rFID | B 等价值/图（内插） | B PSNR / rFID |
|---|---|---|---|
| 1344 | 21.37 / 121.8 | 439 | 19.23 / 173.6 |
| 1920 | 21.73 / 106.9 | 627 | 19.92 / 158.1 |
| 2496 | 21.75 / 106.4 | 815 | 20.53 / 144.0 |
| 3072 | **21.87 / 102.49** | 1003 | **20.94 / 134.1** |

**每像素码率对齐时 A 全面更好**（+0.9 dB，rFID 低约 32），且 A 还少了 3.06× 的相对码率。
这说明周末的两跑**落在同一条"每像素码率–质量"趋势上**：B 的优势几乎全部来自"把分辨率降下来、让同样的 3072 个值去覆盖更少像素"，而不是来自 256×12 这个分配本身。

（该表是内插 + 跨分辨率 FID 指示，不是严格受控结论；但它足以否定"从这两跑能得出 256×12 分配更优"的读法。）

## 5. 同协议下的其他参照点（都为 `fast_rfid`，5000 图 IN-100 val）

| 模型 | 值/图 | PSNR | rFID |
|---|---|---|---|
| **B：256×12@256²，T=8** | 3072 | 22.67 | **86.50** |
| **A：16×192@448²，T=8** | 3072 | 21.87 | 102.49 |
| 16×192@448²，**T=1**（同 s1、同 3ep，只改单步解码） | 3072 | **25.25** | **48.13** |
| 16×448@448²，T=8（K 不变、加宽瓶颈） | 7168 | 23.15 | 63.67 |
| 16×448@448²，T=1 | 7168 | 27.32 | 24.92 |

读法（均为 448² 内部对照，不受跨分辨率问题影响）：
1. **8 步循环解码的税很重**：同为 16×192@448、同 init、同 3ep，T=9→T=1 只把解码从"8 步累计"改成"单步"，PSNR 21.87→25.25 dB（**+3.38**），rFID 102.5→48.1（**2.13×**）。周期解码在 3ep 预算下吃不掉后几步 token。
2. **加宽瓶颈有正收益但抬不动斜率**：K=16 时 192→448 让满速率 rFID 102.5→63.7、PSNR +1.28 dB，但值数也从 3072 涨到 7168（2.33×）。
3. B 相比 A 的 +0.79 dB / rFID −15.6%，在"T=1 能拿到 3.38 dB"面前是**小头**。

## 6. 判定：哪个更好，取决于你问什么

| 问题 | 答案 |
|---|---|
| 谁在**同一 3072 值/图**下的重建质量最好？ | **B（256×12）**：22.67 dB / rFID 86.50，且它是唯一与 ALIT 同口径（256²）的点，差距 10.5×（A 的 12.4× 不是同口径） |
| 谁在**每像素码率**下更高效？ | **A（16×192）** 更好（对齐后 +0.9 dB、rFID −32）；但这是内插+跨分辨率指示，受控性不足 |
| 这两跑能证明"256×12 的 token 分配更优"吗？ | **不能**。分辨率、初始化、预算三个混杂因素都在帮 B；缺 256² 的 16×192 受控臂 |
| 若不受 8 步约束，最好的 3072 值方案？ | **T=1 16×192@448：25.25 dB / rFID 48.1**，明显好于两跑；短板是循环读出，不是分配 |
| 现阶段该沿哪条线继续？ | **B 的 256×12@256² 线**（口径对 ALIT、绝对值最好、且 rFID 在 ep14 仍在快速下降）；但要把"分配结论"和"分辨率结论"分开写 |

一句话给用户：**"数字上 256×12 赢，但这更像'降分辨率到 256²'赢，而不是'256 个细 token'赢；要下 token×dim 的结论，得补 256² 上 16×192 的那一跑。"**

## 7. 最便宜的下一步（建议）

| 优先级 | 实验 | 预算 | 目的 |
|---|---|---|---|
| P0 | **16×192 @256²**：patch 16、K=16、zs_dim=192、T=8 cumulative `1,2,3,5,7,10,13,16`，**从零 14ep、其余完全照抄 B** | ~17.7h（4×S4000） | 补齐同分辨率受控臂，回答 token×dim |
| P1 | 同上的 **3ep** 短预算版 + 评估 B 的 ep3 快照（若远端 `save_every_epochs=1` 的逐 epoch ckpt 仍在） | ~2.5–3h | 便宜 pilot，看方向 |
| P1 | **B 的 T=1 对照**（256²、256×12、单步解码，同 data/预算） | ~2.5–3h | 量化 256² 上的 8 步税（448² 上已知 3.38 dB） |
| P2 | B 继续加轮数到 30–60 ep / 上 refiner（见 `PLAN_refiner_roadmap_20261122.md`） | 13h+ | 压 rFID；ep30 外推 62–65 |

注意：P0 与 B 的**速率点并不完全对齐**（A 的 8 个点按 token 数 1,2,3,5,7,10,13,16），但 384 / 1920 / 3072 三个值数点可直接逐点比；若想全曲线对齐，可在 256² 上把 dec_steps 设计成与 B 同值数（如 32,64,96,128,160,192,224,256 个"1/12 维" 不在同一模型里，做不到——K=16 时只能用 token 数作步数）。**结论：比 3072 满速率点 + 384/1920 两个重叠点即可。**
