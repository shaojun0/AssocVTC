# 240M 基线（降维训练之前）token 的按位置 PCA 冗余分析 —— FINDINGS

**任务**：T2（2026-10-30）。回答用户的问题：「编码器末端 FC 能把每 token 从 1248 维压到 448/224 维而 PSNR 只掉 0.25 dB，
是否说明原始 token 的 PCA 主成分本身是冗余的？」

**数据**：AssocVTC 240M 基线 ckpt（`stdattn_m240_t16/ckpt_best.pt`，step 11406 / epoch 6；ckpt sha256 见
`/userdata/dsh-offload/assocvtc_zpca/tokens/meta.json`）在 ImageNet-100 **val 5000 张**上的 encoder 输出：
`z_s [5000,32,1248] float16`、`z_cls [5000,1,1248]`（T1 产物，脚本 `tools/extract_zs_base_tokens.py`）。
token 文件 sha256 `03bb706b…cda5f0`；无 NaN/Inf。
**分析脚本**：`tools/analyze_zs_pca.py`；**分析机**：本机 8 核 CPU，float64（输入 fp16 → 逐位置 cast float64）。
val 列表按类别分组（每类 50 张连续），逐位置 PCA 对顺序不敏感；split-half 探针用随机置换。

---

## 0. 一句话结论

**是，但要把「位置常量」和「图像相关信息」分开算。** 去掉每个位置的均值后（标准 PCA 口径），
每位置只需 **335 / 1248 ≈ 26.8%** 的主成分就保留 **95%** 的跨图方差，**448 维（35.9% 宽度）保留
98.57%（中位数）**、**224 维（18.0%）保留 88.51%** —— 方差意义上的冗余非常明确。
但两点必须同时写清：(i) 原始 token 能量里**大头是位置常量偏移**（位置均值能量占比中位数 **67.2%**，最高 99.3%），
不居中的 PCA 会把「位置身份」误算成冗余；(ii) 降维臂的 FC 是**跨位置共享**的线性映射，其数据侧最优线性上界
（共享 448 维子空间）只有 **92.87%**（center 方差口径），明显低于「逐位置各用一个 PCA 基」的 98.57%。
所以「FC448 只掉 0.25 dB」不能直接等价于「PCA 前 448 主成分冗余 98.6%」——token 方差保留率 ≠ 图像 PSNR，
零训练的 PCA 截断→解码器对照由 T3（`tools/eval_zs_pca_trunc.py`）直接回答。

## 2. 两个口径：去位置均值 vs 不去 —— 哪个回答「主成分冗余」

| 口径 | rank@95 中位数 | rank@99 中位数 | 前 224 累计方差中位数 | 前 448 累计方差中位数 | 首主成分占比中位数 |
|---|---|---|---|---|---|
| **A. 去位置均值（标准 PCA，主口径）** | **335** | **474** | **0.88511** | **0.98569** | 0.15801 |
| B. 不去均值（二阶矩 PCA） | 185.5 | 372.5 | 0.96271 | 0.99638 | **0.67578** |

- **回答用户「PCA 主成分是否冗余」应看 A**。PCA 的标准定义要求中心化；去均值后的协方差才是「同一位置、
  不同图像之间」的方差，即真正与图像内容相关、压缩时要保留的量。
- B 看起来「更冗余」是假象：不居中时**第一主成分几乎就是位置均值方向**（首 PC 能量占比中位数 0.676，
  近常量位置高达 0.99）；它编码的是「这是第几个 token 位置」这种常量信息，而不是图像信息。
  B 只在回答另一个问题时有用：「一个共享线性映射在 raw 能量上最多能保留多少」。
- 因此本文把三件事分开报：
  1. **图像相关信息（centered）**：逐位置 oracle 前 448 维保留 **0.9857**（中位）/ 0.9819（按位置总方差加权）；
  2. **共享线性映射的图像信息上界**（FC 臂对口）：池化逐位置中心化前 448 维保留 **0.92865**（前 224 维 0.77267）；
  3. **raw 能量上界**（含位置常量）：池化 raw 前 448 维保留 **0.97547**，但其中约 2/3 是位置常量。
- 补充：位置均值向量之间近似正交（两两余弦中位数 0.25），所以「位置常量」不是 1 个方向而是 ~32 个方向；
  共享 FC 无法用一个 bias 把它们整体消掉，这也是共享映射的图像信息上界低于逐位置上界的一个结构性原因。

## 4. 跨位置结构：没有共享主子空间，但每图内部 token 高度冗余

- **位置均值两两近似正交**：余弦中位数 0.2504（均值 0.2067），仅 1.8% 的 pair > 0.9；最大对齐 pair 是
  (20, 30) = 0.973（两个近常量位置），最反相关 (8, 24) = −0.705。
- **主子空间部分共享但远未统一**：top-64 子空间平均主角度中位数 57.28°（随机 ~64.9°），
  重叠 0.347（随机 0.051，**6.8×**）；top-224 平均角 49.68°，重叠 0.448（随机 0.180，**2.5×**）。
  即位置之间共享一些方向，但**不存在一个 32 位置共用的低维子空间**；最好对齐的 pair (7, 31) top-224 平均角仅 21.7°，
  最差 (6, 20) 68.7°。**共享 FC 的 92.87% 上界就是为这种「部分共享」付出的代价。**
- **每图 32 个 token 的跨位置冗余**（每图 32×1248，最大秩 32）：原样 PR 6.60、rank@95 = **20/32**、
  rank@99 = 27/32；**减位置均值后** PR 11.82、rank@95 = **19/32**、rank@99 = 23/32。
  两种口径都说明：同一张图的 32 个 token 并非 32 个独立向量，跨位置有效维数约 7–12（PR），
  95% 跨位置能量约 19–20 维即可覆盖（62% of 32）。这是与「每 token 宽度冗余」方向不同的第二种冗余
  （token 之间/位置之间冗余），对「能否进一步减 token 数」有直接参考价值（本文未做该实验）。
- **z_cls**：与 z_s 位置 token 的冗余程度同量级（rank@95=429、top448=0.9572），且与各位置 top-224 子空间
  的平均主角度 55.4°——它既不是位置均值的简单复制（余弦中位数 0.359），也没有独立出一个新的低维结构。

## 5. 与 448/224 降维臂的对照解读（回答用户假设）

| 口径（oracle，在 5000 张 val 上拟合 PCA） | 448 维保留方差 | 224 维保留方差 |
|---|---|---|
| 逐位置 PCA（每位置一个基底）中位数 | **0.98569** | **0.88511** |
| 逐位置 PCA，按位置总方差加权 | 0.98192 | 0.87457 |
| **共享线性映射的图像信息上界**（池化逐位置中心化，一个 448/224 维子空间） | **0.92865** | **0.77267** |
| 池化全局中心化（参考） | 0.97153 | 0.91473 |
| 池化 raw（含位置常量，参考） | 0.97547 | 0.92669 |
| **实测降维臂（全量微调 3 epoch）** | PSNR 27.688（−0.248 dB） | PSNR 26.083（−1.853 dB） |

**怎么读**：

1. **数据侧冗余是真实的、量级明确的**：即使按最保守的「共享线性映射」口径，448 维也能保留 **92.87%**
   的（平均每位置）centered 方差；按逐位置 oracle 口径是 **98.57%**。1248→448（宽度 −64%）而 PSNR −0.25 dB
   与此方向一致。
2. **但不能把 0.25 dB 直接换算成「98.6% 的冗余」**。降维臂做的是「共享线性投影 + 编码器/解码器全参微调」，
   且 warm start 来自 decoder 权重 SVD（不是数据 PCA）；PSNR 也不是 token 方差的线性函数。
   数据侧上界（92.87%@448）只说明「存在一个 448 维线性瓶颈能保留 92.9% 的 centered 方差」，
   不能直接推出 PSNR 损失。**直接检验见 T3**（零训练 PCA 截断→解码器，`phase2/trunc_eval.json`）。
3. **逐位置 vs 共享的差距本身就是结论**：若允许逐位置（或按位置分组）的线性瓶颈，448 维理论保留率
   98.2–98.6%；共享 FC 只有 92.9%。这与跨位置子空间只部分重叠（top-64 重叠约为随机 6.8 倍、但平均主角度仍 57°）
   互相印证。对后续方法设计的含义：**token 压缩的维度预算可以按位置/位置组非均匀分配**（近常量位置几乎不需要维度，
   内容位置需要更多），这一方向的实验空间比「全部位置共享一个 FC」更大。

## 6. 诚实边界（写报告时必须带上）

1. **PCA 基在测试集上拟合 = oracle / transductive 上界。** 所有保留率、rank、主角度都是在同一批 5000 张
   IN-100 val 上「先拟合后评估」得到的。任何「用训练集拟合、val 上评估」的基（包括 zs448/224 臂）都不会超过该值；
   反过来，本报告的数字**高估**了实际可达到的保留率。降维臂的对照只能作方向性参考。T3 同样是在 val 上拟合 PCA，
   也带 oracle 性质，只是它把「PCA 截断」真正送进了解码器、给出 PSNR 的直接测度。
2. **token 方差保留率 ≠ 重建 PSNR / 任务信息。** 方差是 token 向量的 L2 二阶量；解码器完全可能更依赖某些低方差方向
   （例如符号、边界类别相关的稀疏模式）。因此本报告只能回答「token 向量在 PCA 意义下是否冗余」，
   不能回答「保留 98.6% 方差就一定只掉 0.25 dB」。这是 T3 的职责。
3. **fp16 存储。** token 文件由 fp32 转 fp16（README 口径约为每个坐标的 round-to-nearest，max|Δ|=0.0078，
   token 范数 35.24、坐标 std 0.997）。fp16 相对步长 $2^{-11}\approx4.9\times10^{-4}$，对应量化噪声方差
   $\approx (2^{-11})^2/12\cdot\mathbb E[z^2]\approx \mathbf{2\times10^{-8}}$（相对坐标方差 ~1）。
   实测最小特征值 $\lambda_{\min}\approx3\times10^{-8}$，与噪声量级一致；但所有这些尾部特征值合计
   $<5\times10^{-11}$ 的总方差，**对 rank@90/95/99、top-224/448、PR 无影响**；即使 rank@99.9 的尾部
   （第 ~600–1000 个分量）也远大于量化噪声。结论：fp16 不影响本报告任何结论；理论上若将来要分析尾部
   $<10^{-7}$ 的特征值，应使用 T1 的 fp32 版本。
4. **有限样本（N=5000, D=1248, N/D≈4.0）。** 样本协方差谱有有限样本偏差：rank@固定阈值估计依赖 N。
   split-half 探针（`split_half_probe.json`，位置 0/7/19/26/31，随机对半 2500/2500）：
   - 两半各自拟合的 rank@95 相差 **中位数 1、最大 9**（例如 pos0：全量 424，两半 398/399）；
   - 两半 top-224 子空间平均主角度 **23.5°–28.3°**（随机 ~64.9°），前 100 个解释方差比的 L1 相对差 **1.9%–4.0%**；
   - 说明**主成分结构本身稳定**，但「rank@95 的绝对值」在 N 减半时系统性变小（pos0 424→398），
     故报告中的 rank 应理解为「N=5000 测得的数」，不是总体真值；真实总体的 rank 可能略高。
5. **val 顺序是按类别分组的**（100 类 × 每类 50 张连续，`data_linattn.build_datasets(..., val_per_class=50)`），
   不是随机顺序。逐位置 PCA 对样本顺序不敏感；但若做「按类别/跨类别」的统计需另行设计（本报告未做类别条件分析）。
6. **位置异质性被中位数掩盖**（见 §3）：32 个位置里 7 个近常量、12 个高方差、10 个中方差、2 个半常量、
   1 个（pos 0）最丰富；总方差跨 72×。报告引用中位数时应同时给出 min–max 或分组结论。
7. **token 数（K=32）本身的冗余没有被直接检验**。本报告只处理「每 token 1248 维宽度」的冗余；跨位置冗余
   （§4：每图有效秩约 7–12、rank@95≈20/32）提示 K 可能也能压缩，但需要另行训练/评测，不在 T2 范围。
8. **warm start 是权重 SVD，不是数据 PCA**（§11.1）：zs448/224 臂的 −0.25/−1.85 dB 不能当作「数据 PCA 截断」
   的实测结果；0.25 dB 里有多少来自「token 宽度冗余」、多少来自「全量微调重新分配了编码」，T2 无法拆分。
9. **评测集/模型**：仅 IN-100 val 5000 张、240M 档、K=32、enc_dim=1248、16 步 fixed block2 的基线 ckpt
   （step 11406 / epoch 6）。其它规模/数据集不保证同样的谱形状。
